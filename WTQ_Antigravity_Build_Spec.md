# Utility Bill Decoder: Build Spec

Hand this whole file to Google Antigravity. Build exactly what it says. If something is unclear, pick the simpler option and note it in the README.

Competition: Women Tech Quest, Build Track. Input: electricity bill images (K-Electric, LESCO, IESCO). Output: two CSV files, source code, README, optional demo video.

---

## 0. Hard rules (breaking any of these loses points or disqualifies)

1. LLM: ONLY `gemini-3.5-flash-lite` (primary) or `gemini-3.1-flash-lite` (fallback), through the Google AI Studio API. No other LLM anywhere.
2. NO prebuilt invoice/receipt extractors (Azure prebuilt-invoice, Textract AnalyzeExpense, Mindee, Veryfi, "chat with your PDF" tools). Local OCR such as Tesseract is allowed but not needed. Default is the model reading the image directly.
3. NO hard-coded answers. No test-bill values anywhere in code or data files. Nothing typed or edited into the CSVs by hand. Both CSVs are generated by the code from the templates.
4. Every model, service and library used must be listed in `README.md` and must match the code.
5. Same input must give the same output on a re-run (the Completeness score checks this). Use temperature 0, a fixed seed, and a disk cache.
6. API key lives only in `.env`. Never in code, never in the ZIP.
7. No personal identifiers in any output: names, addresses, CNIC, account, reference, consumer, contract, invoice or meter numbers.
8. Python 3.11+ (state the exact version in the README). `requirements.txt` with exact versions (`package==x.y.z`).
9. ZIP must be 15 MB or smaller. One submission only, so the packaging check (section 11) matters.

## 1. What the system does

```
bill image
   |
   v
[1] image_prep          fix rotation, upscale, make 2 zoomed halves
   |
   v
[2] Level 1 extraction  Gemini vision, strict JSON schema, temp 0
   |
   v
[3] normalize + validate  pure Python (numbers, dates, types, signs, PII guard)
   |        \
   |         -> if checks fail: ONE targeted re-read, then accept and log
   v
[4] level1.csv row

bill image
   |
   v
[5] Bill facts extraction  Gemini vision: usage history, billing history,
   |                       line items with units/rate, message board, printed percentages
   v
[6] Level 2 plan call    Gemini reads 12 questions + L1 + facts, returns per question:
   |                       which numbers are needed + safe math expressions
   v
[7] Python calculator    evaluates the expressions (no LLM arithmetic)
   |
   v
[8] Level 2 write call   Gemini writes plain English answers using the computed numbers
   |
   v
[9] answer checks        non empty, English, no PII, estimates labelled
   |
   v
[10] level2.csv rows
```

Design idea to state in the README and demo: the model does the reading and the language, Python does the arithmetic, validation and file writing.

## 2. Model choice and free tier budget

Both Gemini options have the same free tier limits: 15 requests/min, 250K tokens/min, 500 requests/day.

- Primary: `gemini-3.5-flash-lite`
- Fallback: `gemini-3.1-flash-lite` (switch through `.env`, and auto switch after repeated 429 or 5xx errors)
- On day one, run both on the 5 training bills and keep whichever extracts KESC_0008 closer to the guide's JSON. Default to 3.5.

Request budget for the 10 test bills (worst case per bill: 5 calls):

| Step | Calls per bill |
|---|---|
| Level 1 extraction | 1 (+1 retry max) |
| Bill facts extraction | 1 |
| Level 2 plan | 1 |
| Level 2 write | 1 |

About 50 calls for the real run, about 4 minutes at 12 requests/min. Cap development testing so the 500/day limit is never hit before 12:30 PM.

Rate limiting: a token bucket at `REQUESTS_PER_MINUTE=12` (safety margin under 15), exponential backoff with jitter on 429/5xx, max 5 retries.

SDK: `google-genai` (the current Google Gen AI Python SDK). Use structured output (`response_mime_type="application/json"` plus a response schema from the pydantic models). Check the current docs for exact parameter names for the chosen model. Pin the version you actually install with `pip freeze`.

## 4. Image preparation (`image_prep.py`)

- Open with Pillow, apply EXIF orientation, convert to RGB.
- Bills can be tilted or photographed. Do NOT write heavy deskew code. Tell the model in the prompt that the image may be tilted and partly Urdu.
- Make 3 inputs per bill: full image (long side up to about 2400 px), top half crop, bottom half crop (each upscaled, with a little overlap). Send all three in one call, labelled. Small print on K-Electric bills is the main risk and the crops help with it.
- Set media resolution to high if the SDK supports it.
- Grey boxes are normal. Anything under a grey box is null.

## 5. Level 1: extraction

### 5.1 Output schema (exact, all fields always present)

```json
{
  "provider": "KE | LESCO | IESCO",
  "tariff": "string",
  "sanctioned_load_kw": 0,
  "bill_month": "YYYY-MM",
  "reading_date": "YYYY-MM-DD",
  "issue_date": "YYYY-MM-DD",
  "due_date": "YYYY-MM-DD",
  "previous_reading": 0,
  "current_reading": 0,
  "units_consumed": 0,
  "charges": [{"type": "energy|fixed|fpa|quarterly_adjustment|surcharge|meter_rent|subsidy|other", "amount": 0}],
  "total_charges": 0,
  "taxes": [{"type": "gst|electricity_duty|income_tax|municipal_tax|other_tax", "amount": 0}],
  "total_taxes": 0,
  "current_bill": 0,
  "arrears": 0,
  "payable_within_due_date": 0,
  "payable_after_due_date": 0
}
```

The model schema may carry one extra internal field, `late_payment_amounts: [number]`, which Python reduces to `payable_after_due_date = max(...)` and then deletes before writing the CSV.

Every scalar is nullable. `charges` and `taxes` default to `[]`.

### 5.2 Rules that go into `level1_system.md` (copy these into the prompt)

- Extract values as printed. Do not recalculate, round or correct anything.
- Amounts are numbers in PKR. Remove `Rs.`, commas. `38209CR` becomes `-38209`.
- Credits and subsidies are negative. Previous dues printed as a credit keep their sign (example: `-0.53`).
- Dates: `22nd Sep 2026` becomes `2026-09-22`. `MAR 2026` or `Mar-26` becomes `2026-03`.
- Null for anything not printed, blank, under a grey box or unreadable. Never guess. A correct null scores as correct.
- Do not return names, addresses, CNIC, account, reference, consumer, contract, invoice or meter numbers.
- `provider`: one of KE, LESCO, IESCO. K-Electric (file prefix KESC) is `KE`.
- `tariff`: exactly as printed (`A1-R`, `A-1a(01)`).
- `sanctioned_load_kw`: labelled Sanc Load, S.Load or San Load.
- `due_date`: last date to pay without a late payment surcharge.
- `units_consumed`: units billed this month, as printed.
- `charges`: one entry per line in the charges section. Skip blank lines and lines printed as 0. Keep separate entries when the same type appears more than once (KESC_0008 has two `energy` lines).
- `taxes`: one entry per line in the tax or government section. Classify by the SECTION the line is printed in, not by its name. If only one combined tax amount is printed, return `[]` and put that amount in `total_taxes`.
- `total_charges` and `total_taxes`: the printed subtotals, or null if none printed.
- `payable_after_due_date`: if several late payment amounts are printed, return all of them in `late_payment_amounts` (Python takes the highest).

Charge type mapping:

| Type | Use for |
|---|---|
| energy | Variable Upto ... Units, Cost of Electricity, Energy Charges |
| fixed | Fixed charges |
| fpa | FPA and FCA (both) |
| quarterly_adjustment | QTA, Uniform Quarterly Adjustment |
| surcharge | Additional Surcharge (PHL), F.C Surcharge |
| meter_rent | Meter rent, service rent |
| subsidy | Government subsidy or relief (negative) |
| other | Anything else |

Tax type mapping:

| Type | Use for |
|---|---|
| gst | Sales tax or GST, including GST on FPA |
| electricity_duty | ED |
| income_tax | Income tax |
| municipal_tax | Local charges printed under taxes, such as MUCT (KMC) |
| other_tax | Extra tax, further tax, TV fee, anything else |

Put one short worked example in the prompt (KESC_0008 style) but with the values written generically, not as the real KESC_0008 numbers. The system prompt should not contain any test bill data.

### 5.3 `normalize.py` (deterministic cleanup, pure Python)

- Coerce numeric fields to `int`/`float` (strip `Rs.`, commas, spaces; `CR` suffix means negative). Never return numbers as strings.
- Validate dates with a regex and `datetime`. Bad format becomes null and is logged for a re-read.
- Force charge types into the allowed set (unknown becomes `other`), tax types likewise (unknown becomes `other_tax`).
- Subsidy amounts must be negative: if positive, negate.
- Drop charge lines with amount 0.
- Compute `payable_after_due_date = max(late_payment_amounts)` when present, then remove the internal field.
- Enforce that all 17 top level keys exist, in the schema order.
- Provider cross-check against the file name prefix (KESC maps to KE, LESCO, IESCO). Log mismatches. Trust the image over the file name.
- `json.dumps(..., separators=(",", ":"), ensure_ascii=False)` so it is one line.

### 5.4 `validate.py` (flags only, never silently "corrects")

The guide says do not correct bill amounts, so checks only trigger a re-read:

- `current_reading - previous_reading` close to `units_consumed`
- sum of `charges` close to `total_charges` (when both exist)
- sum of `taxes` close to `total_taxes` (when both exist)
- `total_charges + total_taxes` close to `current_bill`
- dates in logical order, `bill_month` close to the dates

If a check fails: ONE targeted re-read call that names the failing field group and asks the model to look at that part of the bill again. Take the new answer. If the checks still fail, keep the result, write the flag to `logs/`. A printed bill can genuinely not add up, so do not force it.

### 5.5 Optional upgrade (only after everything else works)

Two independent extraction passes (full image vs full + crops), field by field comparison, and a third call only for the disputed fields. Good for the "AI design" score. Skip it if time is short.

## 6. Level 2: answering questions

Questions come from `level2.csv` at runtime (12 questions, same for all 10 bills, 120 rows). The code must be question-agnostic: never write code per question.

### 6.1 Bill facts (`facts.py`)

A second vision call that extracts everything useful beyond the Level 1 schema. This data is for answering questions only and is not written to level1.csv.

```json
{
  "usage_history": [{"month": "YYYY-MM", "units": 0}],
  "billing_history": [{"month": "YYYY-MM", "billed": 0, "paid_date": "YYYY-MM-DD", "paid": 0}],
  "line_items": [{"section": "string", "label": "string", "units": 0, "rate": 0, "amount": 0}],
  "printed_percentages": {"energy_pct": 0, "taxes_pct": 0},
  "late_payment_info": ["string"],
  "message_board": ["string, translated to English"],
  "unclear_or_unreadable": ["string"],
  "other_notes": ["string"]
}
```

- Layouts vary by provider, so every field is nullable or an empty list.
- The 13 month usage bar chart is the hardest part to read. If a bar value is not legible, leave it out and list it under `unclear_or_unreadable`. Do not invent values.
- Still no personal identifiers.

### 6.2 Plan -> compute -> write

**Call A: plan** (`l2_plan_system.md`)

Input: the 12 questions, the Level 1 JSON, the facts JSON. Output, per question:

```json
{
  "question_id": "Q1",
  "interpretation": "which meaning of the question was used (and the other meaning if ambiguous)",
  "answerable_from_bill": true,
  "calculations": [
    {"name": "tax_share_pct", "expression": "pct(l1['total_taxes'], l1['current_bill'])"}
  ],
  "missing_info": "what the bill does not show, or null"
}
```

**Python: `safe_calc.py`**

- Evaluate expressions with `ast` in a restricted evaluator: arithmetic, comparisons, indexing, plus whitelisted helpers: `sum, len, min, max, abs, round, avg(list), pct(part, whole), count_where(list, key, op, value), pluck(list, key)`.
- Namespace: `l1` (Level 1 dict) and `facts` (facts dict). No imports, no attribute access, no function calls other than the whitelist, a length limit on the expression.
- A failed expression yields `"error"` and is passed on so the writer says it could not be computed.

**Call B: write** (`l2_write_system.md`)

Input: question, plan, computed values, Level 1, facts. Output JSON `{ "Q1": "answer", ... }`.

Answer rules to put in the prompt (these are the judge's rules):

- Use only information on the bill. No outside tariff or rate knowledge.
- Use the computed numbers exactly. Do not do arithmetic yourself.
- If the bill does not show something needed, say that clearly instead of guessing.
- Label estimates ("This is an estimate: ...") and say how it was calculated.
- If the question has more than one reasonable meaning, state the one used or answer both.
- English only, even though parts of the bill are in Urdu.
- Specific and short: state the number, the unit (PKR, units, %), and the lines it came from. 2 to 5 sentences. Plain language a customer understands.
- Never include identifiers.

Reference style (from the guide, for how good answers read): "Taxes and duties total PKR 569.62 out of your current bill of PKR 3,430.24, or about 16.6%. The tax lines are sales tax (PKR 520.21), electricity duty (PKR 29.41), and MUCT (KMC) (PKR 20.00)."

### 6.3 Answer checks (`pii_guard.py` and `level2.py`)

- Every answer non empty, string, English. If the model failed for a question, fall back to one more single question call; if that fails, write "The answer could not be determined from this bill image." so no cell is ever empty.
- Scrub digit strings longer than 8 digits and ID looking tokens unless they are money amounts.
- Keep `bill_id`, `question_id` and `question` exactly as in the template.

MVP shortcut if time is tight: skip Call A and pass pre-computed generic metrics (tax share, cost per unit, usage average, max and min month, change vs last month) into one write call. Upgrade to plan -> compute -> write when it is working.

## 7. Reliability

- `llm_client.py`: one function `call_gemini(prompt, images, schema, tag)` used everywhere.
- Cache key: hash of (image bytes, prompt text, model name, schema). Cache hit means no API call. This makes re-runs identical and cheap.
- `temperature=0`, fixed `seed`.
- Per bill try/except: a failing bill never stops the batch. It gets a Level 1 JSON with nulls plus a log entry, and Level 2 answers that say the bill could not be read. No empty cells.
- Resume: skip bills already completed in the cache.
- Logging: one log line per call (bill, step, model, retries, seconds). Summary at the end (flagged bills, retries, failures).

---

## 8. CSV writing (`csv_io.py`)

- Use the `csv` module only. UTF-8. `QUOTE_MINIMAL` quoting (the module doubles inner quotes for you).
- Read the templates, keep row order and the original column names, fill only `json` and `answer`.
- level1.csv: 10 rows. level2.csv: 120 rows.
- After writing, re-read both files and assert: row counts, no empty cells, every json parses to an object with exactly the 17 keys, `bill_id`/`question_id`/`question` identical to the template.

## 12. Final packaging check (`scripts/make_submission.py`)

Builds `submission.zip` with this layout:

```
output/level1.csv
output/level2.csv
source/   (README.md, .env.example, requirements.txt, main.py, app.py, src/, tests/, scripts/)
demo/demo.mp4   (if present)
```

Excludes: `.env`, `cache/`, `venv/`, `__pycache__/`, `input/`, `logs/`, bill images, old zips.

Then the script verifies and prints PASS/FAIL for:

- ZIP size is 15 MB or smaller
- both CSVs exist with 10 and 120 rows, no empty cells, all JSON parses
- `source/README.md`, `source/.env.example`, `source/requirements.txt` exist
- no `.env` file and no string that looks like an API key (for example starts with `AIza`) in any file
- the README contains an "AI usage" section
- the model names in the README match the model names used in the code
- demo file (if present) is .mp4, .mov or .webm
